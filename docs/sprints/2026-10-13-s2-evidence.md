## Acceptance criteria

### R04 / #62: start-code classification

- The skill lists every start code documented in the
  [tool contracts](../tool-contracts.md) in exactly one class: operator
  needed, transient or unknown.
- A test fails if a documented start code is missing from the skill or appears
  in two classes.
- The skill states that classification uses the code only and that unlisted
  codes are unknown. Provider free text is never classified.
- Documentation that mirrors the skill's rules is aligned.
- No runtime, MCP contract or error-code change.

### R13 / #66: bind loaded extension contents

- `prepare` resolves the agent directory once, records it privately, and the
  run's MCP server receives it explicitly as `PI_CODING_AGENT_DIR` for both
  clients.
- When the run uses extensions, the bound resources include each extension's
  package root tree and the agent directory's npm installation, dependencies
  included, under path-free keys. Runs without extensions get a stable `none`
  value.
- A change to any of them between `prepare`, launch and the end of the run
  reports `resourcesChanged` and fails or refuses the run.
- Tests change an extension file, a dependency file and the npm lockfile after
  `prepare` and observe `resourcesChanged` before launch and after a run.
- Tests never read or write the operator's real home or Pi directory. Results
  and evidence stay path-free.
- [Acceptance](../acceptance.md) describes the binding.

### R14 / #67: bind all Codex skill sources

- `prepare` resolves `CODEX_HOME` once and the Codex controller runs with
  exactly that value.
- `$CODEX_HOME/skills` (including the bundled `.system` skills),
  `/etc/codex/skills`, other skills in `~/.agents/skills` and `.agents/skills`
  directories in ancestors of the controller directory are bound under
  path-free keys, as a tree hash or a stable `missing` value.
- A differing `pi-session-orchestration` copy in any source refuses a Codex run
  before launch; an equal copy or none is allowed.
- Evidence states per client whether the controller skill was an installed copy
  (Claude Code) or a run-scoped link (Codex), with its tree hash, without
  paths. Installed and linked skills are distinguishable.
- Tests cover a change in each source, a differing skill in each source, an
  equal copy and a different `CODEX_HOME` at launch, and never touch the
  operator's real home, `CODEX_HOME` or `/etc`.
- [Acceptance](../acceptance.md) lists the sources and the refusal rule.

### Handshake offering / #68

- Two coding profiles: `accept-code` with exactly `implementation` for every
  task, and a separate profile with exactly `implementation` and `handshake`,
  used only for the `slug` session.
- The controller prompt names the profile of each task.
- The skill criterion checks both skill lists and that only the `slug` session
  used the handshake profile; a run in which another task used it fails.
- The scope oracle and `ALLOWED_CHANGES` stay unchanged and strict. This is not
  a wider allowed-file set. Earlier failed attempts stay recorded unchanged.
- [Acceptance](../acceptance.md) describes the two profiles.

### #60: dry-run prediction

- For each retained case of the recovery tests (partial, modified or added-to
  trash; modified backup; foreign staging), `--dry-run` reports
  `skill_recovery_retained` and changes nothing.
- For each settleable case, `--dry-run` still reports `skill_recovery_planned`.
- Classification is shared with the recovery. No second rule set, no new
  persisted state, no name-pattern search and no new report code.
- [Skills](../skills.md#interrupted-updates) and the
  [setup design](../client-setup-design.md) no longer describe the dry-run as
  optimistic.

### Remaining limits recorded by the reviews

- Only skills found by directory name or by a `SKILL.md` frontmatter `name`
  are checked; skills that Codex might load by other means (other file names,
  plugin caches) are not covered. YAML merge keys (`<<`) are not read as a
  name source; it is not established that Codex honors them.
- Exotic but valid frontmatter in an operator's own skills is conservatively
  indeterminate and refuses a Codex run.
- Bound trees are digested by reading whole files; the 200,000-entry cap is
  neither a byte nor a time budget. An unreadable or too large tree fails
  closed with `resourcesUnbound`.
- The Codex controller directory's own `.agents/skills` is bound only through
  the run-scoped link; Codex writing its `.system` skills during a run shows as
  `resourcesChanged` and fails safe.
