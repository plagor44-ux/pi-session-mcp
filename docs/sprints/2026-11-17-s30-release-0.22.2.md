## Findings

1. `npm audit` reports GHSA-fc5q-39xc-vjpf, a regular-expression denial of
   service in `picomatch` up to and including 4.0.7, the newest published
   version. Only the development dependencies `vitest` and `vite` (through
   MCP Inspector) resolve it, `npm audit --omit=dev` reports none, and an npm
   installation contains no `picomatch`. The advisory names no fixed version,
   so no lockfile patch helps. The lockfile of 0.22.1 resolves the same
   version; the report follows from the advisory database. Level 1 and the
   release precondition require 0 vulnerabilities. The maintainer decides
   whether to release with the advisory on record or to wait for a fixed
   `picomatch`.
2. Session history and the provider store live below the home directory of
   the password database. Setting `HOME` or the XDG variables does not move
   them, so a test with a disposable `HOME` still writes the real history.
   The live checks ran in a private mount namespace instead. A documented way
   to point a test server at its own history would make such checks simpler.
   No issue is opened yet.
3. Setup and the host server find the writer root and the setup ownership
   below `HOME`, but the writer launcher resolves the password-database home.
   Under a disposable `HOME`, setup would provision a writer where its
   launcher does not look. The split may be deliberate; it is not
   documented. The live checks used test aliases in the real writer root and
   removed them. Same status as finding 2.
4. The process check of the Level 2 script counts every process whose command
   line contains the name of a setup entry point. The first repetition of
   Level 2 on `7d07431` ran while the review of the release diff ran beside
   it: the review agent received the diff as a command-line argument, the
   diff names those entry points, and each of the four runs failed that one
   check with two such processes. Every other check passed. Level 2 was
   repeated on the head commit with no such process beside it. A check that
   matches the entry point in a process's first arguments, not anywhere in its
   command line, would not depend on what runs beside it. No issue is opened
   yet.

## Roadmap decisions #221 and #144

Both issues need a Mac and stay open; this sprint changes neither.

- [#221](https://github.com/plagor44-ux/pi-session-mcp/issues/221), review
  snapshots on macOS, is the smaller step. Setup already holds an `O_EXLOCK`
  lock on APFS and has the macOS process-table scan, so the slot lock and the
  setup guardian have a base to build on. Proposed as the first macOS item
  once a Mac is available for native tests.
- [#144](https://github.com/plagor44-ux/pi-session-mcp/issues/144), container
  writers on macOS through a Podman machine, is an evaluation with an open
  outcome and needs a Mac with a working Podman machine. Proposed after #221.

## Open proofs for 1.0

Not decided; the list names what the records of 0.22.2 do not establish and
what a 1.0 statement would need.

- A Level 3 cycle on the exact build of a published release, and Level 2 and
  Level 3 on macOS outside CI.
- macOS parity or a documented limit for review snapshots (#221) and for
  coding isolation (#144).
- An abort during a coding session's `read` against a real provider (the
  route of #298).
- A profile with `maxOutputTokens` against a real provider.
- Tier routing with real routed starts, enough verdicts for learning and one
  proposal taken through `apply` and `rollback`.
- A provider store with a stored key and an account sign-in on a release.
- The Claude Code wake with event delivery on a release.
- The acceptance of the second installation (the server host) for a release.
- A rule for development-only advisories without a fixed version (finding 1),
  or a clean `npm audit`.
- A freeze of the public contract: tools, fields, states and error codes.
- For any recommendation between delegation paths: repeated comparisons
  instead of one run per path.
